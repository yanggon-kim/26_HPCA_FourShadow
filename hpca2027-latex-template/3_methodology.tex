
\section{FourShadow Microarchitecture}
\label{sec:design}

\subsection{Overview of FourShadow}
\label{sec:design_overview}

FourShadow adds two components to the base tensor core of Section~\ref{sec:bg_tcu}, the warp-group tensor core (Section~\ref{sec:design_wgmma}), which reads its operands from shared memory through the Warp-Group Tile Buffer Subsystem, and the sparse tensor core (Section~\ref{sec:design_sparse}), which adds 2:4 structured sparsity; Figure~\ref{fig:figure_integration} shows the complete datapath with both. Section~\ref{sec:design_pm} describes the programming model that selects among warp-level MMA, warp-group MMA and their sparse forms at compile time.

\textbf{Warpgroup and tensor blocks.} The warp-group tensor core executes the warp-group MMA (WGMMA) instruction, with which the warps of a warpgroup compute one matrix product, each warp on its own tensor block. The core has one tensor block per issue slot, $\mathit{IW}$ blocks for an issue width of $\mathit{IW}$, and a warp runs on the block selected by its warp index modulo $\mathit{IW}$. Software forms the warpgroup: the kernel launches a cooperative thread array (CTA) of $\mathit{IW}$ warps, and warp $w$ of the CTA owns the $2\,\mathit{tcM}$ output rows that start at row $2w\,\mathit{tcM}$. All warps read the same $B$ tile, so a warpgroup extends the operation in the $M$ dimension only (Figure~\ref{fig:wgmma_tiling_equations}, warp-group tile: only $\mathit{wgTileM}$ grows with $\mathit{IW}$). With $\mathit{NT}{=}32$ and $\mathit{IW}{=}4$, four $8{\times}4$ blocks compute a 64-row tile.

\textbf{Tile and micro-ops.} Each warp's sequencer expands its WGMMA instruction into micro-ops, and one micro-op computes one $\mathit{tcM}{\times}\mathit{tcN}$ block of the output. The per-warp tile is two blocks deep in $M$ and two in $K$; the number of accumulator registers, $\mathit{NRC}\in\{8,16,32\}$, sets its extent in $N$ to $n_{\mathrm{steps}}=\mathit{NRC}/2$ blocks. $\mathit{NRC}{=}8$ is the accumulator count of the base tensor core. The micro-ops run with $k$ outermost, then $n$, then $m$ innermost, and micro-op $(m,n)$ accumulates into register \texttt{f}$(2n{+}m)$. For $\mathit{NT}{=}32$, $\mathit{IW}{=}4$ and FP16 inputs, the warpgroup tile ($M{\times}N{\times}K$) is $64{\times}16{\times}16$ with 16 micro-ops per warp at $\mathit{NRC}{=}8$, and $64{\times}64{\times}16$ with 64 at $\mathit{NRC}{=}32$.

\textbf{Operands and descriptors.} Operand $B$ always comes from shared memory. Operand $A$ comes from shared memory in shared-memory/shared-memory (SS) mode and from four registers, \texttt{f24}--\texttt{f27}, in register/shared-memory (RS) mode. A shared-memory operand is named by a 32-bit descriptor: a 16-bit byte offset from the base of shared memory and a 16-bit row stride. A stride of zero selects the block-major layout, in which the tile is stored as the blocks that the micro-ops consume; a non-zero stride selects a row-major layout for $A$ and a K-major layout for $B$, from which the tile buffer gathers a block row by row. Software places the two descriptors in integer registers \texttt{x10} and \texttt{x11}, and each tensor block latches them at the first compute micro-op of the instruction. The accumulators occupy \texttt{f0} to \texttt{f}$(\mathit{NRC}{-}1)$, so $\mathit{NRC}{=}32$ fills the floating-point register file and is available in SS mode only; RS mode supports $\mathit{NRC}\le 16$. The kernel stages the tiles into shared memory with ordinary loads and stores or with DXA (Section~\ref{sec:bg_smem}), whose row-major output the non-zero-stride layout reads.

\textbf{Tile buffers and the shared-memory port.} Each tensor block has a private $A$ buffer that holds one $K$ stripe of its warp's tile, both $m$ blocks, so the two $m$ micro-ops of a stripe read it without another shared-memory access. The $A$ buffer refills at every new $k$ and at the first compute micro-op of every instruction, because the kernel rewrites the tile in place under an unchanged descriptor. One $B$ buffer is shared: it holds the $B$ block of the current $(k,n)$ and broadcasts it to all tensor blocks. Residency of the $B$ block does not depend on $m$, so one refill serves both $m$ micro-ops of all $\mathit{IW}$ blocks, eight tensor operations for $\mathit{IW}{=}4$, as long as the blocks request the same $(k,n)$. This describes the RTL design, and the simulated runs of Section~\ref{sec:eval_wgmma} realize this sharing: the shared-memory reads of an SS step amount to one $B$ tile per warpgroup, 1.00 at an issue width of four. The $\mathit{IW}{+}1$ buffers share, through a fixed-priority arbiter (the SMEM Read Arbiter of Figure~\ref{fig:figure_integration}), one port that reads a full bank row of $\mathit{NT}$ words per request. This port is the direct-access port of shared memory that DXA writes through, and it has priority over the load/store unit at every bank.

\textbf{Consistency without a barrier.} The warps of a warpgroup are not synchronized cycle by cycle: each warp's sequencer advances independently, and three checks keep the shared state consistent. \emph{(i)~Issue-slot lock.} The first micro-op of an instruction locks its issue slot and the last releases it, so only that warp issues on the slot in between. \emph{(ii)~Single-CTA gate} (the Lockstep block of Figure~\ref{fig:figure_integration}). Each tensor block records the CTA of the instruction it executes from the first to the last compute micro-op, and a WGMMA micro-op waits while another block is inside an instruction of a different CTA. \emph{(iii)~$B$-key match.} The lowest-indexed active block sets the key of the shared $B$ buffer: the offset of the $B$ descriptor, $k$, $n$ and $\mathit{NRC}$. A block whose key differs stalls until the keys agree, and an idle block matches any key, so a CTA with fewer than $\mathit{IW}$ active warps runs unchanged. Each tensor block carries its results through its own result queue to commit.

\textbf{2K-wide FEDP.} The 2K-wide FEDP doubles the dot-product length from $\mathit{tcK}$ to $2\,\mathit{tcK}$ words for every input format, so one micro-op consumes both $K$ blocks of the tile and the dense $K$ steps go from two to one.

In SS mode both halves come from the tile buffers. In dense RS mode a compute micro-op needs two $A$ registers, and its second source field carries the upper half of $A$ in place of the $B$ descriptor; one setup micro-op therefore delivers the $B$ descriptor first, and the compute micro-op for block $m$ reads the lower half of $A$ from \texttt{f}$(24{+}2m)$ and the upper half from \texttt{f}$(25{+}2m)$. The upper half of both operands is zero for WMMA and for sparse WGMMA, which takes one $K$ step with or without the 2K-wide FEDP, so both instructions execute unchanged. We stop at 2K: a wider FEDP makes every unit more expensive and adds fanout across the datapath, and its upper part is idle for every WMMA and sparse instruction.

The second holds the descriptors in the per-warp TCU SRAM that stores the sparse metadata (Section~\ref{sec:design_sparse}) in place of \texttt{x10} and \texttt{x11}: the warp writes its descriptors to shared memory and loads them with the metadata-load instruction. This relieves the register file, and its cost is a shared-memory store, a CTA barrier and a load through the load/store unit before the first micro-op.

\subsection{Sparse Tensor Core}\label{sec:design_sparse}

\textbf{2:4 Structured Sparsity.} The sparse tensor core executes WMMA and WGMMA on a matrix $A$ pruned with 2:4 structured sparsity: every group of four consecutive elements along $K$ in a row of $A$ keeps two. $A$ is stored compressed, as its kept elements, with metadata whose bits mark the kept positions of each row; $B$ stays dense.

\textbf{Microarchitecture.} Figure~\ref{fig:figure_integration} draws the sparse tensor core as the 2:4 Structured Sparsity Subsystem, between the operands and the FEDP arrays. The Metadata AGU Load block brings the metadata into the Metadata TCU SRAM. The Sparse MUX Array receives matrix $B$ and the metadata of the current micro-op and selects, for each row of $A$, the two elements of every group of four $B$ candidates that match the kept positions of that row (one of every two for 32-bit inputs); in the Selection MUX inset, metadata 1001 selects $b_0$ and $b_3$. The array has one selector per FEDP unit, because the rows of $A$ keep different positions of the same $B$ candidates. A multiplexer passes the selected $B$, or the unmodified $B$ of a dense instruction, to the Pipeline Buffer. Compressed $A$ reaches the FEDP arrays as stored, without inserted zeros, so an FEDP unit computes as many products as in a dense micro-op but covers twice the positions of $K$, which halves the $K$ steps of a tile.

\textbf{Sparse Metadata Flow.} Before sparse execution the kernel calls \texttt{load\_sp\_metadata}, which emits one warp-level instruction, \texttt{TCU\_LD}: each lane contributes one 32-bit metadata word, and a warp-level address generation unit (AGU) issues the load as an ordinary load/store request. The request is routed by its address like any other load, to global or to shared memory; our sparse kernels keep the metadata in global memory. The returned words are written to the metadata SRAM of every tensor block, indexed by warp, and a micro-op reads the part selected by its $m$ and $k$ steps, so any tensor block can run that warp's sparse micro-ops. In the RTL the scoreboard orders the two operations: the decoder marks the metadata load as the writer of a reserved per-warp scoreboard bit and every sparse MMA as a reader of it, and the bit is released by the writeback of the load, which the AGU raises in the cycle it writes the SRAM, so a sparse MMA issues only after its metadata is written, without a software-visible fence.

\textbf{Asymmetric vs.\ Symmetric Configurations.} The halved $K$ steps halve the micro-ops of a sparse WMMA only in the asymmetric configurations of Section~\ref{sec:bg_tcu} ($\mathit{NT}{\in}\{2,8,32\}$), a consequence of the RISC-V instruction encoding. A sparse micro-op needs twice the $B$ of a dense one (the red ``$\times$2 col candidates'' of Figure~\ref{fig:figure_register_mapping}). In the asymmetric case, panel~(a) with $\mathit{NT}{=}8$, a dense block of $B$ occupies half a register, so the doubled block fits in the one $B$ register that the micro-op already reads (red \texttt{reg0}). In the red annotations, $\mathit{xtileK}$ halves from 8 to 4 and $k_{\mathrm{steps}}$ from 4 to 2, so the micro-ops halve from 32 to 16 with every FEDP unit active.

In the symmetric case, panel~(b) with $\mathit{NT}{=}4$, a dense block of $B$, $\mathit{tcK}{\times}\mathit{tcN} = 2{\times}2$ words, already fills a register, and the doubled block would need a fifth source register. A micro-op has four register fields, inherited from the R4-type \texttt{fmadd} encoding, all occupied by $A$, $B$, $C$ and $D$. The symmetric configurations therefore halve $\mathit{tcN}$ from 2 to 1, which doubles $n_{\mathrm{steps}}$ from 2 to 4 while $k_{\mathrm{steps}}$ halves from 2 to 1 (red annotations of panel~(b)): a thread mask activates half the FEDP units in each micro-op, and the micro-op count stays at 16.

\subsection{Programming Model}
\begin{figure}
    \centering

    \caption{FourShadow Programming Model}
    \label{fig:sw_integrationv4}
\end{figure}
\label{sec:sw_integrationv4}\label{sec:design_pm}

FourShadow exposes WMMA, WGMMA, and 2:4 structured sparsity as composable primitives selected almost entirely at compile time. Input/output format (\texttt{ITYPE}/\texttt{OTYPE}), NRC, and RS-versus-SS mode (Section~\ref{sec:design_wgmma}) are all template parameters on \texttt{wgmma\_config\_t} and \texttt{wgmma\_context} (Figure~\ref{fig:sw_integrationv4}), so the same kernel source compiles down to dense WMMA, dense WGMMA, or sparse WGMMA execution depending on how it is instantiated.

\textbf{Metadata packing.} On the host, \texttt{pack\_metadata\_wg} repacks the 2:4 mask produced by pruning/compression into the per-thread SRAM bank layout that the \texttt{TCU\_LD} AGU and the metadata SRAM expect (Section~\ref{sec:design_sparse}); the layout is dimensioned against the \emph{WMMA}-config per-warp depth, since that shared hardware is sized for WMMA.

\textbf{Operand and metadata delivery.} In the kernel, \texttt{load\_sp\_metadata} loads the packed mask in both RS and SS mode (Section~\ref{sec:design_sparse}), and $A$ reaches the instruction as Section~\ref{sec:design_wgmma} describes, through \texttt{load\_matrix\_sync} in RS mode and through a descriptor built by \texttt{vx\_make\_smem\_desc} in SS mode; both modes call the same \texttt{wgmma\_sync} entry point.

\textbf{Tile Stride.} Each warp's private $A$ section is padded to the shared-memory bank-row width ($\mathit{NT}\times\mathrm{XLEN}/8$ bytes) so warp $w{+}1$'s stripe always starts on a fresh bank row. Without this, the $A$ buffer's single-row fetch can walk into the previous warp's region.
