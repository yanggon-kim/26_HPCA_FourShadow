
\section{FourShadow Microarchitecture}

\subsection{Overview of FourShadow}
\label{sec:design_overview}

\begin{figure*}[ht]
    \centering
    \includegraphics[width=\textwidth]{hpca2027-latex-template/fig/fourshadow_uarch.pdf}
    \caption{FourShadow's complete datapath: the warp-group tensor core and the sparse tensor core added to the base tensor core of a Vortex SIMT core.}
    \label{fig:figure_integration}
\end{figure*}

FourShadow adds two components to the base tensor core of Section~\ref{sec:bg_tcu}, the warp-group tensor core and the sparse tensor core; these are the extensions that the rest of this section describes, and Figure~\ref{fig:figure_integration} shows the complete datapath with both. The warp-group tensor core (Section~\ref{sec:design_wgmma}) makes the warps of a warpgroup execute one matrix operation, one tensor block per warp, with operands read from shared memory through the Warp-Group Tile Buffer Subsystem: one private $A$ buffer per tensor block and one $B$ buffer shared by all blocks. The sparse tensor core (Section~\ref{sec:design_sparse}) adds 2:4 structured sparsity: a metadata SRAM in every tensor block and a Selection Mux Array that picks the $B$ elements matching the retained $A$ elements. Section~\ref{sec:design_pm} describes the programming model that selects among warp-level MMA, warp-group MMA and their sparse forms at compile time.

\textbf{Warpgroup and tensor blocks.} The warp-group tensor core executes the warp-group MMA (WGMMA) instruction, with which the warps of a warpgroup compute one matrix product, each warp on its own tensor block. The core has one tensor block per issue slot, $\mathit{IW}$ blocks for an issue width of $\mathit{IW}$, and a warp runs on the block selected by its warp index modulo $\mathit{IW}$. Software forms the warpgroup: the kernel launches a cooperative thread array (CTA) of $\mathit{IW}$ warps, and warp $w$ of the CTA owns the $2\,\mathit{tcM}$ output rows that start at row $2w\,\mathit{tcM}$. All warps read the same $B$ tile, so a warpgroup extends the operation in the $M$ dimension only (Figure~\ref{fig:wgmma_tiling_equations}, tile ownership: $A^{(w)}$ and $C^{(w)}$ depend on $w$, $B^{(\mathrm{wg})}$ does not). With $\mathit{NT}{=}32$ and $\mathit{IW}{=}4$, four $8{\times}4$ blocks compute a 64-row tile.

\textbf{Tile and micro-ops.} Each warp's sequencer expands its WGMMA instruction into micro-ops, and one micro-op computes one $\mathit{tcM}{\times}\mathit{tcN}$ block of the output. The per-warp tile is two blocks deep in $M$ and two in $K$; the number of accumulator registers, $\mathit{NRC}\in\{8,16,32\}$, sets its extent in $N$ to $n_{\mathrm{steps}}=\mathit{NRC}/2$ blocks. $\mathit{NRC}{=}8$ is the accumulator count of the base tensor core. The micro-ops run with $k$ outermost, then $n$, then $m$ innermost, and micro-op $(m,n)$ accumulates into register \texttt{f}$(2n{+}m)$. For $\mathit{NT}{=}32$, $\mathit{IW}{=}4$ and FP16 inputs:
\[
\begin{array}{c|c|c}
\mathit{NRC} & \text{warpgroup tile } (M{\times}N{\times}K) & \text{micro-ops per warp} \\ \hline
8  & 64\times16\times16 & 16\\
16 & 64\times32\times16 & 32\\
32 & 64\times64\times16 & 64
\end{array}
\]

\textbf{Operands and descriptors.} Operand $B$ always comes from shared memory. Operand $A$ comes from shared memory in shared-memory/shared-memory (SS) mode and from four registers, \texttt{f24}--\texttt{f27}, in register/shared-memory (RS) mode. A shared-memory operand is named by a 32-bit descriptor: a 16-bit byte offset from the base of shared memory and a 16-bit row stride. A stride of zero selects the block-major layout, in which the tile is stored as the blocks that the micro-ops consume; a non-zero stride selects a row-major layout for $A$ and a K-major layout for $B$, from which the tile buffer gathers a block row by row. Software places the two descriptors in integer registers \texttt{x10} and \texttt{x11}, and each tensor block latches them at the first compute micro-op of the instruction. The accumulators occupy \texttt{f0} to \texttt{f}$(\mathit{NRC}{-}1)$, so $\mathit{NRC}{=}32$ fills the floating-point register file and is available in SS mode only; RS mode supports $\mathit{NRC}\le 16$. The kernel stages the tiles into shared memory with ordinary loads and stores or with DXA (Section~\ref{sec:bg_smem}), whose row-major output the non-zero-stride layout reads.

\textbf{Tile buffers and the shared-memory port.} Each tensor block has a private $A$ buffer that holds one $K$ stripe of its warp's tile, both $m$ blocks, so the two $m$ micro-ops of a stripe read it without another shared-memory access. The $A$ buffer refills at every new $k$ and at the first compute micro-op of every instruction, because the kernel rewrites the tile in place under an unchanged descriptor. One $B$ buffer is shared: it holds the $B$ block of the current $(k,n)$ and broadcasts it to all tensor blocks. Residency of the $B$ block does not depend on $m$, so one refill serves both $m$ micro-ops of all $\mathit{IW}$ blocks, eight tensor operations for $\mathit{IW}{=}4$, as long as the blocks request the same $(k,n)$. The $\mathit{IW}{+}1$ buffers share, through a fixed-priority arbiter (the SMEM Read Arbiter of Figure~\ref{fig:figure_integration}), one port that reads a full bank row of $\mathit{NT}$ words per request. This port is the direct-access port of shared memory that DXA writes through, and it has priority over the load/store unit at every bank.

\textbf{Consistency without a barrier.} The warps of a warpgroup are not synchronized cycle by cycle: each warp's sequencer advances independently, and three checks keep the shared state consistent. \emph{(i)~Issue-slot lock.} The first micro-op of an instruction locks its issue slot and the last releases it, so only that warp issues on the slot in between. \emph{(ii)~Single-CTA gate} (the Lockstep block of Figure~\ref{fig:figure_integration}). Each tensor block records the CTA of the instruction it executes from the first to the last compute micro-op, and a WGMMA micro-op waits while another block is inside an instruction of a different CTA. \emph{(iii)~$B$-key match.} The lowest-indexed active block sets the key of the shared $B$ buffer: the offset of the $B$ descriptor, $k$, $n$ and $\mathit{NRC}$. A block whose key differs stalls until the keys agree, and an idle block matches any key, so a CTA with fewer than $\mathit{IW}$ active warps runs unchanged. Each tensor block carries its results through its own result queue to commit.

\textbf{2K-wide FEDP.} The 2K-wide FEDP doubles the dot-product length from $\mathit{tcK}$ to $2\,\mathit{tcK}$ words, so one micro-op consumes both $K$ blocks of the tile and the dense $K$ steps go from two to one (Figure~\ref{fig:fedp2k_blocks}: the $K$ extent of the block doubles for every input format).

\begin{figure}
    \centering
    \includegraphics[width=0.8\linewidth]{hpca2027-latex-template/fig/fedp2k.pdf}
    \caption{Logical K vs 2K-Wide FEDP}
    \label{fig:fedp2k_blocks}
\end{figure}

In SS mode both halves come from the tile buffers. In dense RS mode a compute micro-op needs two $A$ registers, and its second source field carries the upper half of $A$ in place of the $B$ descriptor; one setup micro-op therefore delivers the $B$ descriptor first, and the compute micro-op for block $m$ reads the lower half of $A$ from \texttt{f}$(24{+}2m)$ and the upper half from \texttt{f}$(25{+}2m)$. The upper half of both operands is zero for WMMA and for sparse WGMMA, which takes one $K$ step with or without the 2K-wide FEDP, so both instructions execute unchanged. We stop at 2K: a wider FEDP makes every unit more expensive and adds fanout across the datapath, and its upper part is idle for every WMMA and sparse instruction.

The first deepens the FEDP pipeline from four to eight cycles, to absorb the longer multiply and accumulate stages of a 2K-wide unit; its cost is a longer latency for every WMMA and WGMMA micro-op.

The second holds the descriptors in the per-warp TCU SRAM that stores the sparse metadata (Section~\ref{sec:design_sparse}) in place of \texttt{x10} and \texttt{x11}: the warp writes its descriptors to shared memory and loads them with the metadata-load instruction. This relieves the register file, and its cost is a shared-memory store, a CTA barrier and a load through the load/store unit before the first micro-op.

\subsection{Sparse Tensor Core}\label{sec:design_sparse}

\textbf{Analytic Speedup Model.}
Figure~\ref{fig:sparse_analytic} captures an analytic model of the speedup derived from adding a 2:4 structure sparsity subsystem to the TCU. The dense cost is normalized to~1 and sparsity halves the compute term~$\mathit{TC}$ but adds metadata overhead $\mathit{MO}$ that grows linearly as the input datatype narrows.

\begin{figure}[ht]
\small
\raggedright
\hrule
\vspace{3pt}
\noindent\textbf{Dense (normalized to 1):}
\begin{equation}
\mathit{Cycle}_{\text{dense}} = A_{\text{load}} + B_{\text{load}} + \mathit{TC} + D_{\text{store}} = 1
\end{equation}
\noindent\textbf{Sparse:}
\begin{equation}
\mathit{Cycle}_{\text{sparse}} = A_{\text{load}} \!\times\! s_{\text{eff}} + B_{\text{load}} + \tfrac{1}{2}\,\mathit{TC} + D_{\text{store}}
\end{equation}
\noindent\textbf{Speedup and effective saving:}
\begin{equation}
\mathit{Speedup} = \frac{1}{\mathit{Cycle}_{\text{sparse}}}, \qquad
s_{\text{eff}} = 1 - \tfrac{1}{2} + \mathit{MO}
\end{equation}
\noindent where $\mathit{MO}$ is the metadata overhead relative to matrix~$A$:
\begin{equation}
\mathit{MO} = \frac{\texttt{sizeof}(\texttt{input\_dtype})}{32}

\end{equation}

\textbf{Sparse Metadata Flow.} One of the main modifications to the TCU microarchitecture here is the addition of the metadata operand inputs. Metadata has different lifetime and reuse properties than $A$ and $B$, so it moves through a separate path. Before sparse execution, the kernel issues \texttt{load\_sp\_metadata}, which emits one warp-level instruction, \texttt{TCU\_LD}: each participating lane contributes one 32-bit metadata word, and a warp-level address generation unit (AGU) forms the load as an ordinary load/store-scheduler request rather than a tensor tile-buffer fetch, so metadata can live in either global or local memory. The returned lane words are assembled into a warp metadata record and written identically into every tensor block's metadata SRAM, indexed by warp identity with subregions selected by the current $m$ and $k$ coordinates. Replication means any issue path can run that warp's sparse micro-ops, rather than tying the warp to whichever block happened to complete its metadata load. A scoreboard dependency orders the two operations: the metadata load produces a reserved token, and sparse execution consumes it, so sparse micro-ops cannot issue until the load returns and its SRAM write completes. This removes the need for a separate software-visible metadata fence.

\textbf{Sparse FEDP Selection.} The compressed $A$ values are sent directly to the FEDP inputs; the hardware does not reconstruct a dense vector by inserting zeros. Instead, the row-specific metadata drives the Selection Mux Array as a gather network on the $B$ side, selecting the two $B$ elements that match the two retained $A$ positions for each group of four. This selector is replicated across the FEDP grid because metadata is row-dependent: different $A$ rows can retain different positions even though the underlying $B$ candidates are shared. A sparse micro-operation still performs eight nonzero products per output element, but those products now cover sixteen logical $K$ positions instead of eight, so sparse execution needs only half as many $k\_steps$ as dense execution for the same tile.

\textbf{Asymmetric vs.\ Symmetric Configurations.} Enabling 2:4 sparsity halves matrix~$A$'s $K$ dimension, reducing both load volume and MMA micro-ops ($k\_steps$ halved) at the cost of metadata. The $B$ operand preparation, however, differs fundamentally between asymmetric and symmetric configurations, and the performance benefit applies only to the asymmetric group ($\mathit{NT}{\in}\{2,8,32\}$).

Figure~\ref{fig:figure_register_mapping}(a) shows the asymmetric case of Section~\ref{sec:bg_tcu} for $\mathit{NT}{=}8$. With sparsity enabled (red), each compressed $A$ row must pair with two candidate $B$ columns for metadata-driven selection, changing the $B$ layout to vertical column pairs (``$\times$2 col candidates''). Because a dense $B$ block occupies half of each register, this rearrangement fits within the existing width. As shown in the red annotations, $\mathit{xtileK}$ halves from 8 to 4, reducing $k\_steps$ from 4 to 2 while all FEDP units remain fully active.

In the symmetric case, Figure~\ref{fig:figure_register_mapping}(b) with $\mathit{NT}{=}4$, each dense $B$ block of $\mathit{tcK}{\times}\mathit{tcN} = 2{\times}2 = 4$ already fills a register. Doubling the $B$ columns for sparsity would require a fifth source operand, but FourShadow's datapath, inherited from Vortex's R4-type \texttt{fmadd} path, supplies exactly four register fields, all occupied by the micro-op encoding for $A$, $B$, $C$, and $D$. Instead, as shown in the red annotations, we halve $\mathit{tcN}$ from 2 to 1, doubling $n\_steps$ from 2 to 4. Although $k\_steps$ halves from 2 to 1, the total micro-op count remains 16, with only half the FEDP units active per micro-op, alternating via thread masks. Consequently, the symmetric group achieves barely any speedup from sparsity, but FourShadow preserves full configurability across all thread counts.

\subsection{Programming Model}

    \caption{FourShadow Programming Model}

FourShadow exposes WMMA, WGMMA, and 2:4 structured sparsity as composable primitives selected almost entirely at compile time. Input/output format, NRC, and RS-versus-SS mode are all template parameters on \texttt{wgmma\_config\_t} and \texttt{wgmma\_context} (Figure~\ref{fig:sw_integrationv4}), so the same kernel source compiles down to dense WMMA, dense WGMMA, or sparse WGMMA execution depending on how it is instantiated.

\subsubsection{Host-Side Data Preparation}

\textbf{Metadata Packing.} The 2:4 mask produced by pruning/compression is not uploaded as-is; \texttt{pack\_metadata\_wg} repacks it into the per-thread SRAM bank layout that the \texttt{TCU\_LD} AGU and the metadata SRAM expect (Section~\ref{sec:design_sparse}). That layout is dimensioned against the \emph{WMMA}-config per-warp depth since the \texttt{TCU\_LD} path and metadata SRAM are shared hardware sized for WMMA.

\textbf{Compile-Time Mode Selection.} The RS and SS modes and their $\mathit{NRC}$ ranges are those of Section~\ref{sec:design_wgmma}. Both RS/SS and format (\texttt{ITYPE}/\texttt{OTYPE}) are template parameters, fixed at build time.

\subsubsection{Kernel-Side Orchestration}

\textbf{Tile Stride.} Each warp's private $A$ section is padded to the shared-memory bank-row width ($\mathit{NT}\times\mathrm{XLEN}/8$ bytes) so warp $w{+}1$'s stripe always starts on a fresh bank row. Without this, the $A$ buffer's single-row fetch can walk into the previous warp's region.

\textbf{Sparse Metadata and Descriptor Dispatch.} Unlike $A$ and $B$, the packed sparse mask bypasses shared memory entirely: \texttt{load\_sp\_metadata} reads it straight from global memory into the TCU's metadata SRAM before dispatch, in both RS and SS mode. The two modes then diverge only in how $A$ reaches the instruction, register fragment via \texttt{load\_matrix\_sync} for RS, shared-memory descriptor via \texttt{vx\_make\_smem\_desc} for SS, but both call the same \texttt{wgmma\_sync} entry point. Sparsity itself is selected once, at compile time, by instantiating \texttt{wgmma\_context} with its sparse flag set, not by a differently named sparse instruction per launch.
