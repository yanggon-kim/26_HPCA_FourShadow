\section{Background}
\label{sec:background}

This section describes the base tensor core that FourShadow extends and the concepts it depends on: the SIMT hierarchy, the issue width with its warpgroups, and shared memory.

\subsection{SIMT Hierarchy and Threads per Warp}
\label{sec:bg_hierarchy}

The base tensor core is built into Vortex~\cite{vortex}, an open-source RISC-V GPU. A Vortex processor is organized as clusters of cores; inside a cluster, a socket groups the cores that share first-level caches.

Each core is a SIMT pipeline that runs $\mathit{NW}$ warps. A warp is a group of $\mathit{NT}$ threads that execute the same instruction on $\mathit{NT}$ lanes of the datapath, so the threads per warp ($\mathit{NT}$) set the width of every per-thread structure: the register file holds $\mathit{NT}$ entries per architectural register, and the load/store unit has $\mathit{NT}$ lanes. Both $\mathit{NW}$ and $\mathit{NT}$ are compile-time parameters.

\subsection{Base Tensor Core}
\label{sec:bg_tcu}

The base tensor core is the Tensor Core Unit (TCU), a functional unit in the execute stage of each core beside the ALU, FPU, LSU and SFU (Figure~\ref{fig:figure_integration}). It shares the core's front end, register file, shared memory and caches with those units, and it executes the warp-level MMA (WMMA) instruction. Its compute engine is a grid of Fused Dot Product (FEDP) units, each of which computes one element of $D$:
\begin{equation}
\label{eq:fedp}
D_{m,n} =
\sum_{i=0}^{K-1}
\left(A_{m,i} \times B_{i,n}\right) + C_{m,n}.
\end{equation}
Figure~\ref{fig:tiling_equations} derives the tile, the block and the steps from the threads per warp $\mathit{NT}$; $\mathit{NT}{=}8$ is the running example.

\textbf{Matrix-Register Mapping:}
Vortex's RV32 ISA provides 32 floating-point registers per thread. The base tensor core uses 24 of them, $\mathit{NR}{=}8$ each for matrices $A$, $B$ and the accumulator $C/D$. A register holds $\mathit{NT}$ 32-bit entries, so each matrix has a budget of $\mathit{NT}{\times}\mathit{NR}$ words. A \emph{tile} is the part of each matrix that one WMMA instruction covers within this budget (the Tile equations of Figure~\ref{fig:tiling_equations}). Panels (a) and (b) of Figure~\ref{fig:figure_register_mapping} show in green how the eight registers of each matrix cover the $8{\times}8{\times}8$ tile ($M{\times}N{\times}K$) of $\mathit{NT}{=}8$ and the $8{\times}4{\times}4$ tile of $\mathit{NT}{=}4$. A 32-bit entry packs two 16-bit or four 8-bit inputs, so a tile covers that many times more elements of $K$ ($\mathit{tileK}$, the last Tile equation).

\textbf{Thread-FEDP Mapping:}
A \emph{block} is the part of a tile that one \emph{micro-op} computes on the $\mathit{NT}$ FEDP units (the Block equations of Figure~\ref{fig:tiling_equations}): the units form a $\mathit{tcM}{\times}\mathit{tcN}$ grid, and each takes a dot product of $\mathit{tcK}$ words. The block is $4{\times}2{\times}2$ for $\mathit{NT}{=}8$ and $2{\times}2{\times}2$ for $\mathit{NT}{=}4$; for $\mathit{NT}{=}32$ it is $8{\times}4{\times}4$ for 32-bit inputs, $8{\times}4{\times}8$ for 16-bit inputs and $8{\times}4{\times}16$ for 8-bit inputs. A configuration is \emph{asymmetric} when a block of $B$ occupies half a register, so that two adjacent blocks pack into one register ($\mathit{NT}{\in}\{2,\allowbreak 8,\allowbreak 32\}$; panel (a)), and \emph{symmetric} when a block of $B$ fills a whole register ($\mathit{NT}{\in}\{4,16\}$; panel (b)). The \emph{steps} $m_{\mathrm{steps}}$, $n_{\mathrm{steps}}$ and $k_{\mathrm{steps}}$ are the blocks per tile in each dimension (the Steps equation), 2, 4 and 4 for $\mathit{NT}{=}8$. A WMMA instruction executes one micro-op per block, with $n$ innermost, $m$ in the middle and $k$ outermost (the loop nest of Figure~\ref{fig:tiling_equations}): 32 micro-ops for $\mathit{NT}{=}8$ and 16 for $\mathit{NT}{=}4$.

Each micro-op reads three source registers, one each for $A$, $B$ and $C/D$, from a register file divided into four banks. The registers of matrix $B$ are relocated so that the three sources fall in different banks and are read in the same cycle.

\textbf{FEDP Microarchitecture \& Datatypes:}\label{para:datatypes-fedp} The FEDP unit is Ten-Four~\cite{rout2026tenfouropensourcefuseddot}, a four-stage, four-cycle design (multiply, align, accumulate, normalize and round) with a configurable dot-product length. It multiplies TF32, FP16, BF16, FP8 (E4M3), BF8 (E5M2), INT8 and INT4 inputs and accumulates in FP32 or INT32; each input format is enabled or disabled at compile time.

\subsection{Issue Width and Warpgroups}
\label{sec:bg_issue}

The issue width is the number of warps from which a core issues an instruction in the same cycle. The issue stage is divided into that many issue slots, and the warps are interleaved over the slots by warp index, so each slot serves $\mathit{NW}$ divided by the issue width warps. An issue width of one issues from a single warp per cycle.

The tensor core scales with the issue width: the core instantiates one tensor block, a complete $\mathit{NT}$-unit FEDP grid, per issue slot. The warps that issue together, one from each slot, form a \emph{warpgroup}; the size of a warpgroup therefore equals the issue width, and the tensor blocks of a core can serve all warps of one warpgroup in the same cycle. On NVIDIA GPUs a warp has 32 threads and a warp group has four warps~\cite{luo2025dissectingnvidiahopperarchitecture}; that point corresponds to $\mathit{NT}{=}32$ and an issue width of four here. The instruction that makes the warps of a warpgroup cooperate on one matrix operation is part of our design (Section~\ref{sec:design_wgmma}).

\subsection{Shared Memory and DXA}
\label{sec:bg_smem}

Shared memory is a scratchpad private to each core and shared by the warps that run on it. It is divided into $\mathit{NT}$ banks, one per thread of a warp, and consecutive words fall into consecutive banks, so the $\mathit{NT}$ threads of a warp read or write $\mathit{NT}$ consecutive words through $\mathit{NT}$ different banks. Each bank holds 2\,KB with a floor of 8\,KB for the whole memory, which gives 8, 16, 32 and 64\,KB for $\mathit{NT}$ of 4, 8, 16 and 32.

A kernel fills shared memory from global memory either with ordinary per-thread loads and stores or through DXA. DXA is Vortex's counterpart of the Tensor Memory Accelerator of NVIDIA Hopper~\cite{nvidia2022hopper}: a warp issues one instruction that names a pre-programmed descriptor of a tile, and an engine shared by the cores of a socket copies that tile from global memory into shared memory asynchronously while the warp continues with other work. The warp-group tensor core of Section~\ref{sec:design_wgmma} reads its operands from shared memory.

\section{Motivation}
\label{sec:motivation}

A commercial tensor core cannot be opened; only its behavior can be measured from outside. FourShadow is its \emph{white-box counterpart}: an open design that implements the same features with internals that can be read and changed. The name has two meanings. As a \emph{shadow}, it outlines an object that cannot be inspected, in four components: the base tensor core, the warp-group tensor core, the sparse tensor core and the programming model; the behavior behind the outline is the subject of Q1 (Section~\ref{sec:mot_causes}). As a \emph{foreshadow}, being reconfigurable, it foretells the trends, sweeps and Pareto curves of design points that no commercial GPU ships, the subject of Q2 (Section~\ref{sec:mot_point}).

\subsection{Q1: What Is the Microarchitectural Behavior Behind NVIDIA's Tensor-Core Features?}
\label{sec:mot_causes}

Vendor documents and microbenchmarking studies report what each tensor-core feature delivers. NVIDIA states that 2:4 sparsity doubles tensor-core throughput~\cite{nvidia2020ampere}, yet the GEMM speedup approaches 2$\times$ only for larger GEMMs~\cite{mishra2021acceleratingsparsedeepneural}. On an H800, sparse \texttt{mma} instructions average 1.42$\times$ the dense throughput, and the sparse warp-group MMA instruction takes 128 cycles with matrix $A$ in registers and 144 with $A$ in shared memory~\cite{luo2025dissectingnvidiahopperarchitecture} (Section~\ref{sec:eval_wg_delivery} gives the mechanism). These sources show the outcome but give no clue to the internal microarchitecture, the mechanism that produces it.

Simulation frameworks cannot supply the mechanism either, because they abstract the tensor core. Accel-Sim~\cite{accel-sim} gives every tensor-core instruction one latency and one initiation interval, both read from a single configuration option. Its micro-op sequence, the delivery of its operands from registers or shared memory, and its sparsity metadata are below the resolution of such a model, which cannot attribute a measured outcome to any one of them. GPGPU-Sim~\cite{raihan2019modeling} also models the tensor core inside a cycle-level simulator. Table~\ref{tab:related_work_comparison} places both among related platforms: every GPU platform except CoopWarp~\cite{nada2025cooperative} fixes the warp at 32 threads, Accel-Sim and GPGPU-Sim have no sparsity, Accel-Sim models warp-group MMA only as a latency, and no prior platform combines FourShadow's configurable thread counts, data types, 2:4 sparsity, warp-group MMA and open RTL. The eight other platforms support one to four data types each; FourShadow supports seven: TF32, FP16, BF16, FP8, BF8, INT8 and INT4.

\subsection{Q2: How Does a Tensor Core Behave as Its Architectural Parameters Change?}
\label{sec:mot_point}

A commercial GPU ships one point of the tensor-core design space: its threads per warp and issue width are fixed in silicon, on NVIDIA GPUs at the warp and warp-group sizes of Section~\ref{sec:bg_issue}. Microbenchmarking studies measure that point across GPU generations, instruction shapes and data types~\cite{jia2018dissectingnvidiavoltagpu, jia2019dissectingnvidiaturingt4, 9931992, luo2025dissectingnvidiahopperarchitecture}. The interaction of the two, such as the return of a wider issue width at 32 threads per warp against 16 or 4, therefore cannot be measured on any shipped part. A simulation framework can change both parameters, but the model of Section~\ref{sec:mot_causes} has no tensor-core organization to vary with them. The design points around the shipped one are unmeasured and their headroom unexplored.

\textbf{Open source and answers to the two motivating questions.} FourShadow is an open, synthesizable and reconfigurable tensor-core microarchitecture that obtains the causes by design-space exploration, changing one microarchitectural parameter at a time. For Q1 we measure it beside a commercial GPU: where the two agree, the mechanism visible in FourShadow is a candidate explanation; where they differ, the difference excludes one. For Q2, its best design point is the best on this counterpart and carries over to a commercial design only as far as the two match. Neither question can be approached without such an open, reconfigurable design. Section~\ref{sec:design} presents FourShadow; the Evaluation then answers Q2 in Section~\ref{sec:eval_hierarchy} and Q1 in Sections~\ref{sec:eval_wgmma} and~\ref{sec:eval_sparse}.
